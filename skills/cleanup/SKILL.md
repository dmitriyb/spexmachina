**Commits and pushes:** yes. This skill commits and pushes its changes and opens a PR. Enforcement hook `check-skill-commit-allowed.sh` permits `git commit` when the active skill is `cleanup`.

First run `git checkout main && git pull --rebase` to ensure you are on the latest main.

Handle the cleanup bead $ARGUMENTS. This skill is for beads labeled `spex:cleanup` — work generated by `spex apply` when a component was removed from the spec but its code had already shipped. Your job is **removal**, not implementation.

If the bead is NOT labeled `spex:cleanup`, stop immediately and tell the user — they probably want `/implement` instead.

## Context Loading

Cleanup beads do not have a `spex:<record-id>` label and do not have a bead-map record. Context comes from three sources:

1. Run `br show $ARGUMENTS --json` to read the cleanup bead's labels, dependencies, and title.
2. **Predecessor bead** — find the `blocks:<old-bead-id>` dependency; that is the obsoleted feature bead whose code needs removing. Run `br show <old-bead-id> --json` to read its title and description. The title gives you the component name (e.g. `apply: ProposalTagger`) and the description describes what the component did — that's the scope of removal.
3. **Proposal** — read the `spec_proposal:<ref>` label, then open `spec/proposals/<ref>.md` to understand why the component was removed and what, if anything, replaces it. The proposal often names the replacement mechanism so you can verify the intended end state.

If any of these are missing (no `blocks:` dep, no `spec_proposal:` label), stop and tell the user — the cleanup bead lacks traceability and you should not guess.

## Pre-flight Checks

Run ALL of the following. If ANY fails, **STOP immediately**, report the failure, and do NOT proceed.

### Check 1: Bead label

The bead must carry the `spex:cleanup` label. If not, this is not a cleanup bead — use `/implement` instead.

### Check 2: Bead status

The bead must be in `open` or `ready` status. If `in_progress`, `closed`, or tombstoned, stop.

### Check 3: Git signing key available

Run `ssh-add -l` and verify at least one key is loaded. If no keys are found, stop and tell the user:

> Cannot clean up $ARGUMENTS — no SSH signing key available in the agent. Run `ssh-add` to load your key before proceeding.

Do NOT bypass signing with `--no-gpg-sign` or `-c commit.gpgsign=false`.

### Check 4: Predecessor bead is closed

The `blocks:<old-bead-id>` dep must point to a closed bead. If it is still open or in_progress, stop — the component's original work has not shipped yet, so there is nothing to clean up. Tell the user to finish the predecessor first.

## Workflow (Removal)

1. **Claim the bead:** `br update $ARGUMENTS --status in_progress`.

2. **Create a branch:** `git checkout -b cleanup/<component-name> origin/main` — use a short kebab-case name derived from the component (e.g. `cleanup/proposal-tagger`).

3. **Identify the code to remove.** You need to find every file, function, struct, test, import, and reference that ties back to the removed component. Use the component name from the predecessor bead's title as your anchor:

   ```bash
   # Case-insensitive + identifier-level hits (whole-word with snake / camel / kebab variants)
   git grep -niE '(proposal[_ -]?tagger|ProposalTagger)' -- ':!.beads' ':!spec' ':!*.md'

   # Spec history — files that were deleted by the proposal's merge (context only, do not edit)
   git log --oneline --diff-filter=D -- 'spec/<module>/arch_<name>.md' 'spec/<module>/impl_<name>.md'
   ```

   Record every hit. Typical categories:
   - Core implementation file(s) (e.g. `apply/proposal_tagger.go`)
   - Direct unit test file(s) (e.g. `apply/proposal_tagger_test.go`)
   - Usage sites: constructors, wiring (look for the struct name or constructor function in `apply/run.go`, `cmd/spex/*.go`, etc.)
   - Imports that become unused after the removal
   - Test fixtures or setup helpers that only existed for this component
   - Documentation references outside of git history (e.g. README, `docs/`)

4. **Remove it.** Delete the implementation and test files. Update every usage site to no longer reference the component — most commonly this means removing a call site or struct field. Do not add backward-compatibility shims or fallback stubs.

5. **Fix the resulting compile errors.** If removing the component leaves orphaned callers, those callers must either be removed too, or (if they remain valid) reshaped to use whatever replaced the component. The proposal tells you which.

6. **Remove obsolete tests.** Tests that exercised only the removed component are deleted. Tests whose coverage shifts to the replacement mechanism should be updated to call the new code path, not deleted — only drop tests that become tautological.

7. **Do NOT write new tests.** Cleanup is removal. If you find yourself authoring a new test to prove "the component is gone", stop — a passing `go build ./... && go test ./...` with zero references to the component is the proof.

8. **Completion gate** (see below). Do NOT proceed until every item passes.

9. **Commit and push.** Commit message pattern:

   ```
   Close <bead-id>: remove <component-name> (<module>)

   <1-2 sentences on why the component was removed, per the proposal>

   Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
   ```

10. **Open a PR** using `.github/pull_request_template.md`. Body should include the cleanup bead ID, the predecessor bead ID, and the proposal reference.

11. **Link the bead:** `br update $ARGUMENTS --external-ref "PR#<number>"`, commit `.beads/issues.jsonl`, push.

## Completion Gate

Before committing, verify ALL of the following:

1. **Zero identifier references.** Run:

   ```bash
   git grep -niE '<component-identifier-patterns>' -- ':!.beads' ':!*.md'
   ```

   Zero hits outside git history = done. If any remain, either remove them or explain why they are unrelated false positives (e.g. a library function with a coincidentally similar name).

2. **Build clean.** `go build ./...` succeeds. `go vet ./...` reports nothing.

3. **Tests green.** `go test ./...` passes. Test count should drop (you removed at least the component's own tests); if it stayed the same, check whether you missed the test file.

4. **No dead imports.** `goimports -l ./...` is empty, or `gofmt -l ./...` if goimports is not available.

5. **No TODO/FIXME referencing the removed component.** `git grep -niE '(TODO|FIXME|HACK).*(<component-name>|<old-bead-id>)'` returns nothing.

6. **Proposal satisfied.** Re-read the relevant section of `spec/proposals/<ref>.md`. The proposal's stated end state — "X is gone, Y replaces it" — must hold after your changes.

## Non-goals

- Do NOT implement new behavior. If the proposal describes a replacement mechanism, that is a separate feature bead and NOT your job.
- Do NOT refactor unrelated code along the way. Keep the diff tightly scoped to removal + the minimum reshaping of call sites.
- Do NOT reintroduce the removed behavior under a new name. Deprecation shims are a common anti-pattern; trust the proposal.

## When something looks wrong

- **Predecessor bead still open or in_progress:** stop. The apply pipeline should not have produced a cleanup bead for an unshipped component; flag it.
- **No `blocks:` dep on the cleanup bead:** stop. This bead predates the fix in `spexmachina-idd` or was created by a different mechanism. Ask the user before proceeding — the removal scope is ambiguous.
- **Component name from the predecessor bead matches zero files:** stop. Either the code was already removed, or you are searching the wrong identifier. Confirm with the user before closing the bead as a no-op.
