# Change Proposal: Set declared field values

## Context

`2026-09-14-authoring-commands` gave the spec a write path: nodes are declared, removed and renamed by command, edges are added and removed by command, leaves are scaffolded by command, and every write is refused with the validator's own error or reported with what it obliges. It left one edit out. Changing a value on an existing node — a requirement's `description`, a project requirement's `priority`, a component's or an api's `description`, the `derivation: pending` flag a bootstrapping project removes once a module derives the requirement — has no command. The rewritten `/spec` skill says so in as many words: it is "the one JSON edit made by hand, on the entry alone, and `spex diff` reports what it obliges."

That exception sits under the most common alteration there is. Every drift triage changes a requirement's description. Most correction proposals do nothing else. The adoption path removes `derivation: pending` once per requirement. So the write path is deterministic for the rare edits and manual for the frequent one, and the obligation that edit incurs — a requirement description change obliges a changed leaf on every implementing component, the rule that makes proposals larger than they look — is the one obligation still discovered at the end of a session by `spex diff` instead of printed when it is incurred.

The gap is small in code and large in what it lets the skill claim. `NodeEditor` (`cb8ef2b70999`) already decides a field's kind, requiredness and enumeration from the profile when a node is added and already routes every write through `ObligationReporter` (`b9e7b96f6aa7`); setting a field on an existing entry is the same decision over an entry that exists. This lands in the v0.4.0 window with the authoring commands, so that the release means "authoring is deterministic" without a footnote.

## Proposed change

### `spex node set`

A ninth api in the `author` module, a child of the existing `spex node` grouping: `spex node set <id> --field <name>=<value>`, repeatable, plus `--unset <name>` to remove an optional field. It replaces the value of a declared field on the node the id names, at either scope, in whichever file holds the entry.

What it accepts is what the profile declares for the node's type as a non-reference field — text, integer, enumeration — and the envelope's `description`. Values are converted by kind exactly as `spex node add` converts them, so an integer field refuses a non-integer and an enumerated field refuses a value outside its enumeration, each with the validator's own entry and the declared kind or enumeration as the fix.

What it refuses, each with the command that does the job as the fix:

| Field | Refusal names |
|---|---|
| `name` | `spex node rename` — the name is the identity |
| `id`, `content` | nothing: both are derived, never set |
| a reference field — `implements`, `uses`, `describes`, `provided_by`, `preq_id`, `depends_on` | `spex edge add` / `spex edge remove` |
| a field the type does not declare | the type's declared fields |
| a module id | the hand edit, as `remove` and `rename` already do for frame nodes |

`--unset` on a required field is refused with the validator's `schema` entry, the same one a hand edit deleting the field would earn. Setting a field to the value it already holds changes nothing and says so; unsetting a field that is absent does the same.

### The write is `NodeEditor`'s, through the reporter

`NodeEditor` owns the command beside add and remove: the entry is rewritten in place, in the same canonical form every other write uses, and the after-state goes through `ObligationReporter` before anything reaches disk. The report carries the obligations the change incurred — for a module requirement's description, every implementing component's leaf; for a project requirement, the walk down through every deriving module requirement to every implementing component; for a component's or api's description, its own leaf where the rules say so and nothing otherwise. This is the obligation that today surfaces only from `spex diff` at the end of a session.

### What it does not do

It edits no reference field, no name and no content path; those have their own commands, and a field with two write paths is a field that can be edited inconsistently. It does not touch a module entry. It reads nothing under `.spex/`, needs no initialised project, and runs no subprocess, like every command in the module.

### Why not extend an existing surface

`spex node add` with an existing id was considered and rejected: add creates and refuses duplicates, and an upsert would make "did this create or change a node" a question about the tree's prior state rather than about the command. `spex edge add` was considered for `description` and rejected because description is not an edge. A separate command whose name says what it does is the shape the rest of the module has.

### Work riding with the epic

The `/spec` skill loses its scalar-field exception paragraph and its report item for hand edits: the write path has no exception left. `docs/commands.md` gains the command under Authoring. The cli module is untouched: a child of an existing grouping adds no constructor, so the bounded-surface requirement's count does not move and `RootCommand` owes nothing.

### The checks that can actually fail

Setting a module requirement's description must print, under `obligations`, exactly the implementing components' leaves and nothing else, and the same edit made by hand must make `spex diff` report the same entries — the parity oracle every command in the module is held to. Setting a project requirement's `priority` must land in `project.json` and print nothing when no leaf is obliged. `--unset derivation` on a project requirement that a module requirement now derives must leave `spex validate` green and remove the disclosure note; `--unset` on `type` must be refused with the `schema` entry. Setting `name` must be refused naming `spex node rename`; setting `implements` must be refused naming `spex edge add`. Setting a field to its current value must leave the tree byte-identical.

### Scope

Four tasks under one epic: three component leaves — `NodeEditor`, `AuthorCommands`, and the flow — and one test section. One requirement and one api are added; nothing is renamed or removed. The code is one command on `NodeEditor` and its wiring in `AuthorCommands`.
