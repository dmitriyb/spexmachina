# Change Proposal: Profile v2 — declared fields

## Context

`2026-08-20-declarative-profile` (epic h4gv) turned the node-type *containers* into data: a profile declares type names, their plural array keys, scope, content-bearing flags, coverage chains and graph policy, and the schemas are composed from it. What it did not turn into data is the *shape* of a node. Every field beyond the generic envelope — a requirement's `priority` and `type` enum, an api's `group` and `provided_by`, the reference fields `implements`, `uses`, `describes`, `preq_id`, `depends_on` — lives in the frame's built-in `$defs`, reachable only by the five built-in type names. A profile-declared type gets a closed envelope: `id`, `name`, `description`, optionally `content`, and nothing else (`additionalProperties: false`).

Two consequences trigger this proposal:

1. **The declared-edge half of the taxonomy is undeliverable for custom types.** Requirement `5392cca550c4` says the profile declares "which reference fields a type may carry", yet the composition never reads the profile's edge declarations, so a custom type cannot carry any reference field at all — no DAG participation, no coverage chain with a custom-type source. Filed as `drifts/drift-spexmachina-h4gv.1.json` against ModuleSchema (`78883b84c32d`) and resolved by the drift triage inside epic h4gv: composition now specifies one array-of-identity-hash property per declared edge kind whose source names the type, guarded by an interim profile-validation rule refusing a new edge kind sourced at a built-in type. What that fix deliberately leaves out — and this proposal delivers — is the *field* half, and built-in types joining the same composition path.
2. **The default ontology cannot be expressed as a profile.** The built-in types needed rich fields; custom types are denied exactly what the built-ins demonstrably required. The mechanism fails its own dogfood test, and the policy that decides what counts as a semantic change (`hashed_fields`) mirrors frame internals instead of deriving from declarations.

A third, related gap: no authored document declares which format version it speaks. The SchemaLoader leaf records the deliberate deferral ("No schema versioning is needed initially"); with the profile becoming the carrier of the whole data model, that deferral expires — a binary must be able to say "this profile/spec/journal predates me, migrate" instead of failing with a cascade of conformance errors. The changeset already models this (`changeset.json` is explicitly v3); authored inputs deserve the same.

Release note: the edge defect shipped as a point fix inside epic h4gv — custom types carry declared edges now. This proposal generalizes that mechanism rather than introducing it: edge declarations become reference-kind field declarations, and the interim refusal of edge kinds sourced at built-in types is retired once built-ins compose through the same path.

## Proposed change

All changes land in the **schema** module, with one consumer change in **merkle** and matching test-section updates.

### 1. Field declarations per node type (taxonomy, `5392cca550c4` — modified)

Each declared node type gains a list of field declarations. A field declares: its name; its kind — text, integer, or reference; whether it is required; whether it participates in the node's hash (default: yes); for text fields an optional enumeration of permitted values; for integer fields optional bounds; for reference fields the permitted target node types, the cardinality (one or many), and the optional `cyclic` exemption the edge set carries today. A reference-kind field *is* the edge declaration: the separate `edges` section of the v1 profile format is unified into the source type's field list, so one declaration answers "what may this type carry, what may it point at, and does it count as a semantic change". Coverage-chain triples and the DAG check name the field on its declaring type, exactly as they name an edge kind today. The envelope minimum (`id`, `name`, `description`, `content` where content-bearing), the identity-hash algorithm, the name tokenization rule, the merkle tree shape and the journal event format remain fixed points a profile cannot reach. `requires_module` on module declarations stays in the frame: modules are not profile-declared types.

### 2. Composition materializes declared fields (`ef55248cb3ca`, ProjectSchema `79946d618829`, ModuleSchema `78883b84c32d`, SchemaLoader `ee88263d6555` — modified)

The composed schema for each declared type carries one property per declared field — typed, bounded, enum-constrained, identity-hash-patterned for references — under the same `additionalProperties: false`. The built-in `$defs` leave the frame: the five built-in types' shapes are composed from the default profile's field declarations through the same path every custom type takes, so built-ins stop being special by construction — and the interim profile-validation rule refusing a new edge kind sourced at a built-in type is retired by the same move. The frame retains only the envelope, the identity-hash pattern, the root document shapes and `additionalProperties: false`. The golden criterion of v1 is kept and extended: composing from the default profile reproduces the shipped static schema documents as JSON values, and every identity hash, validation report and diff on this repository's spec is unchanged.

### 3. The default profile becomes embedded data (`b7c3bccd7c64`, ProfileLoader `cd726f8b088b` — modified)

The built-in default profile is an embedded `defaultProfile.json` — a document in the source tree, parsed at startup, identical in format to what a project may commit as `spec/profile.json` — rather than hand-authored Go values. The readable golden policy record the v1 leaves promise becomes an actual JSON document a newcomer can open. ProfileLoader's resolution contract is unchanged (file when present, embedded default otherwise, one early failure on malformed input); its exposure changes shape: the resolved profile is handed to consumers as interned declarations — each node type and field resolved once, consumers comparing resolved references rather than strings, iteration order being declaration order — which is what keeps per-node work in validate/diff free of repeated name lookups (the `Fast` bound, `afc25fb6c8e8`, and `Fast validation`, `b42c5cdf874b`, both hold at 100 modules / 1000 nodes).

### 4. Hashed-field policy derives from declarations (`91270a8a2b57` — modified; TreeBuilder `dfe1467b7a4b` — modified)

The per-type `hashed_fields` allowlist map is retired. A JSON-backed node's hashed serialization is derived from its type's field declarations: every declared field participates unless declared `hashed: false`, plus the envelope fields that participate today. The default profile's declarations reproduce today's allowlists exactly, so no existing hash moves. Coverage chains, the plan-relevant set, impact levels and absorbable directions remain declared graph rules as in v1.

### 5. Format versioning (new module requirement in schema; SchemaLoader `ee88263d6555`, BeadMapSchema `d125b5e775b4`, `f7ef8bef0ba1`, `f471f2764ab8` — modified)

One new module requirement, **Declare the format version** (derives from project requirement `Validate spec structure`, `d5a8407d38e1`), specifying three version declarations, all metadata outside the hashed payload:

- `profile_version` in the profile document (the profile is not a merkle leaf, so the field is invisible to the tree). The binary declares the versions it supports; a profile outside that range fails early with one message naming the file, its version and the supported range — the "migrate before using this spex" signal, replacing a cascade of conformance errors.
- `spec_version` in `project.json` only — one declaration per project. `project.json`'s envelope leaf (`meta/project`) is inert by the existing tree contract: its change produces one structural diff entry, obliges no component leaf and mints no bead, so introducing the field costs a single refresh-absorbable entry. Module files carry no version — a per-`module.json` field would move every module's `meta` leaf and trigger the change-completeness rule against every component, an adoption cost with no information gain over the single project-level declaration.
- an optional per-line `v` in the journal-line format, absent meaning version 1. The journal is append-only and permanent: readers accept every version from 1 forward, forever; a writer stamps the current version. No existing line changes meaning.

Absent version fields mean version 1 — today's format — so adoption is, again, doing nothing. The SchemaLoader leaf's deferral sentence is superseded by this contract.

### 6. Validation of the profile document (ProfileLoader `cd726f8b088b` — modified)

Profile validation extends over the new declarations: a field with an unknown kind, a reference field naming an undeclared target type, an enum on a non-text field, bounds on a non-integer field, a duplicate field name within a type, or a field name colliding with an envelope field is each a distinct early error naming the declaration. The v1 rule stands: a profile attempting to declare a fixed point fails validation.

## Impact expectation

All work lands as modifications to existing nodes plus one new module requirement; no new components, apis or modules.

**Modified schema requirements (leaf-obliging):** `5392cca550c4`, `ef55248cb3ca`, `91270a8a2b57`, `b7c3bccd7c64`, `f7ef8bef0ba1`, `f471f2764ab8`, plus the new **Declare the format version** (`preq_id` `d5a8407d38e1`). Each description change obliges changed content leaves on the implementing components — all of which change anyway (next item), so the completeness rules are satisfied by the work itself.

**Modified components — one bead each:** ProfileLoader `cd726f8b088b`, SchemaLoader `ee88263d6555`, ProjectSchema `79946d618829`, ModuleSchema `78883b84c32d`, BeadMapSchema `d125b5e775b4` (schema module); TreeBuilder `dfe1467b7a4b` (merkle). Six component beads.

**Modified test sections:** Schema validation tests `96f944302b78` (field composition scenarios; S27 — already carrying the declared-edge variants from the h4gv fix — extended with enum/bounds/cardinality rejections), Schema loading tests `8719672c7580` (defaultProfile.json parsing, version-range refusal, golden comparisons), Hashing tests `31b096a76fd4` in merkle (hashed serialization derived from declarations; existing-hash stability). Test sections describing ≥ 2 components produce beads; expect 2–3 test beads.

**Changed content leaves:** `arch_profile_loader.md`, `arch_schema_loader.md`, `arch_project_schema.md`, `arch_module_schema.md`, `arch_bead_map_schema.md` (schema); `arch_tree_builder.md` (merkle); the test leaves above. Module meta leaves for schema and merkle move with their `module.json` edits; the changed requirement descriptions suppress the meta completeness rule in both modules.

**Estimated scope:** roughly 8–10 beads — six component beads, 2–3 test-section beads, the epic bead. An order of magnitude smaller than h4gv, because h4gv already moved every consumer onto the resolved profile; this change is confined to what the profile declares and how the schema module materializes it.

**Drift resolution:** resolved before this proposal runs — `drift-spexmachina-h4gv.1` was triaged inside epic h4gv, the spec specifies declared-edge composition, and the implementation is born as beads `spexmachina-h4gv.43`–`.48`. This proposal builds on that fix rather than carrying it.

**Baseline:** this proposal births work — a mint, not a refresh.
