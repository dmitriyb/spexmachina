# Change Proposal: Reduce the task map to its irreducible pair

## Context

`.bead-map.json` links each plan-relevant spec node to the task it produced in an external tracker. It is the artifact that keeps `spex` tracker-agnostic: the changeset format is tool-neutral, an adapter translates it, and the map is where `spex` records what the adapter created. Swapping `br` for Jira means writing a new adapter and rewriting values in a file this project owns.

A conceptual draft (`spec/proposals/drafts/post-decouple-architectural-cleanup.md`, commit `dce73d6`) proposes eliminating the map entirely and moving the linkage onto the tasks themselves, as a `spex:<spec_node_id>` label. A full measurement of that idea found it feasible — the pipeline produces a changeset byte-identical to today's apart from label values, with roughly 1,161 fewer lines of production Go — and its core claim is correct: **of the ten record fields, eight are derivable or dead.** Six have zero non-test readers.

But elimination trades the abstraction boundary for those lines. It makes `spex emit` require a tracker view it has never needed, makes the planner depend on `created_at` ordering because 33 record-ids are carried by more than one task across a modify lineage, and moves the adapter's `ref:spec_node` resolution from a local file read to a tracker query. Any future adapter would then need queryable, export-surviving labels rather than merely create, close and an identifier. The spec already records this judgement: `spec/map/arch_mapping_store.md` § *Why not bead labels?* states that labels "coupl[e] spex to the bead CLI's label format" and that "the mapping file gives spex full control over the data structure."

The measurement's sharpest finding is what settles it. Under elimination, 31 of 168 existing tasks carry a `spex:<int>` whose record was already deleted, so their spec node is unrecoverable from any artifact this project owns — and a partial label migration fails **silently**, dropping the close op and creating a duplicate task while the original stays open, because the invariants that would catch it are the ones being deleted.

So the problem is not that the map exists. The problem is that it is a denormalized cache carrying eight fields it does not need, and that it is named after one adapter. This proposal reduces and renames it instead.

It assumes the `2026-07-25-declarative-spec-contracts` migration has landed — api nodes exist, arch leaves carry no Go signatures, and cross-references are hash links.

## Proposed change

### The record becomes two fields

```json
{ "records": [ { "spec_node_id": "f7775ac5f1f3", "task_id": "spexmachina-phb.13" } ] }
```

Dropped, with the measured justification for each:

| field | why it goes |
|---|---|
| `next_id` | a top-level counter, currently 83 against 61 records, that exists only to hand out `id` |
| `id` | integer whose sole purpose is forming the `spex:<int>` label |
| `bead_type` | zero non-test readers; written from the changeset op's node kind, then never read back |
| `node_type` | zero non-test readers; proposal epics are already identifiable by a slug-shaped `spec_node_id` |
| `module` | derivable — resolving a node against `module.json` yields it |
| `component` | zero non-test readers; pure denormalization |
| `content_file` | derivable, and measurably stale: five records carry an empty value where derivation produces the correct path |
| `spec_hash` | derivable from the snapshot. This is the field that drifts, the reason `--mode refresh` exists, and 58 lines of git churn on every refresh |
| `bead_status` | zero non-test readers and absent from the file on disk |

`spec_node_id` and `task_id` remain. `bead_id` is renamed `task_id` in the same pass.

### The file and schema are renamed

`.bead-map.json` → `.task-map.json`; `schema/bead-map.schema.json` → `schema/task-map.schema.json`. The `--map` flag on `spex ingest` and `--map-file` on `spex map` default to the new path. The `map` module name is already adapter-neutral and does not change.

### The label keys on the spec node, and the map stays authoritative

The idempotency label becomes `spex:<spec_node_id>`, generated by `IdempotencyLabeler` from the changeset op rather than from a stored counter, matching the shape `spex:cleanup-<hash>` already uses. `impact/bead_reader.go` stops parsing the label as an integer.

Crucially, `spex` reads linkage from the map, never from the label. The label is an adapter-side idempotency key. That is what makes this change safe where elimination is not: **existing tasks carrying `spex:<int>` need no migration.** They become inert history rather than broken linkage, and the 31 tasks whose records were already deleted stay harmlessly stale instead of becoming unrecoverable. This should be verified before implementation by confirming that a modify pair against a pre-existing task still emits the correct close op with the old label form present.

### Context resolution derives instead of caching

`ContextResolver` locates a node by identity hash across `module.json` files and returns the same fields, rather than reading `module` and `content_file` from a record. Measured against every spec-backed record, this reproduces the store's output exactly except for the five where the store is wrong.

### Consequential edits elsewhere

`Reconciler` in `ingest` maintains two fields instead of nine, so its create-variant table and metadata lookups go. `IdempotencyLabeler` in `emit` loses its cursor and its store dependency. The bead-map schema component in `schema` is renamed in prose and reduced. `scripts/apply-br.sh` emits and probes the new label form.

Three drifts are corrected in passing: `arch_mapping_store.md` locates the file at `spec/.bead-map.json` when it is at the repository root; the same leaf says the file is "maintained by `spex apply`", a command that no longer exists; and § *Why auto-incrementing record IDs?* documents a field this proposal removes and is replaced by the rationale for keying on the spec node.

## Impact expectation

No node is added, removed or renamed. Every spec change is a modification, so no obsolete-plus-create pair arises from restructuring — only from the content edits below.

**Content leaves that must change.** All four `map` module requirements have their descriptions edited, and every one names record metadata this proposal removes. Under the completeness rules that obliges a changed content leaf on each implementing component, and the `module.json` edit moves the module's `meta` leaf, which independently obliges every component in the module. Both are satisfied by the same set: `arch_mapping_store.md`, `arch_map_command.md`, `arch_context_resolver.md` and `flow_bead_mapping.md`.

Outside `map`: `arch_reconciler.md` in `ingest`, `arch_idempotency_labeler.md` in `emit`, and the bead-map schema arch leaf in `schema` — each obliged by its own module's `module.json` edit.

**Beads.** Roughly six bead-producing nodes are modified — three `map` components (`MappingStore` `205e67ca4aad`, `MapCommand` `08909d62930b`, `ContextResolver` `6b79188dff4c`), one `map` data flow (`Bead creation mapping flow` `38b6d99f08bf`), `Reconciler`, `IdempotencyLabeler`, plus the schema component — each producing an obsolete-plus-create pair, so on the order of a dozen operations. Project requirement `Map spec nodes to beads` `9120788210c9` is not edited, which avoids the far larger completeness cascade a project-requirement change triggers.

**Data migration.** One pass rewriting `.bead-map.json` into `.task-map.json` with two fields per record. It is mechanical, reversible while the old file remains in git history, and it touches no external system — the contrast with elimination, which requires rewriting labels on 112 tasks in a tracker where all 168 lines are closed-task lines and therefore need reviewer or owner role.

**Not in scope.** Deleting the `map` module, merging `impact` and `emit`, and collapsing `ingest` are the remaining ideas in the `dce73d6` draft. They are module supersession and legitimately produce bead lifecycle; they belong in a separate proposal after this one, and they become cheaper once the map is two fields.

## Adjacent: the meta rule that inflates this proposal, and every description-only edit

The completeness cost recorded above — the `module.json` edit "independently obliges every component in the module" — is not specific to this proposal. It is the standing price of touching any `module.json`, including a one-word correction to a component `description`.

The cause is attribution, not the rule itself. In `merkle/tree_builder.go` a requirement leaf hashes its own JSON fields, so editing a requirement's description moves *that requirement's* leaf and the completeness checker can name it: only its implementors are obliged. A component, data_flow or test_section leaf hashes only its content file; its `description`, `name` and edges live nowhere but the module-wide `meta` leaf, which is a hash of the entire `module.json`. So when one component's description changes, the tree can report only that *something* in `module.json` moved, and the rule blames every component in the module because it has no way to tell which one.

The fix is to give those three node types the treatment requirements already get: hash each leaf over its content file **and** its own `module.json` entry. The `meta` leaf then covers what its name claims — the module envelope: module name, module description, `requires_module`, and the set of node ids. A description edit becomes a change to one node, handled by the existing targeted rule. A node added or removed still moves `meta` and still stops the pipeline.

This makes enforcement sharper, not weaker. Today an author who corrects one word is handed a wall of errors whose only practical exit is a blanket `--mode refresh`, which absorbs everything indiscriminately — the outcome the rule exists to prevent. Pointed at the single node they touched, the correct response is obvious and cheap. Carrying a separate content hash and metadata hash per node would go further and let `refresh` distinguish a rename from a rewritten contract, a line it cannot currently draw and one this proposal's removal of `spec_hash` leaves entirely to the snapshot.

Out of scope here: it is a `merkle` change requiring its own snapshot rewrite, and belongs in its own proposal.
