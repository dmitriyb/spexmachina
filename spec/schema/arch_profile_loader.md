# ProfileLoader

ProfileLoader owns the resolution of the project's spec profile: the declarative document that turns the node-type vocabulary from compiled-in policy into data. It reads `spec/profile.json` when the file exists, falls back to the built-in default profile otherwise, validates the document, and exposes the resolved profile to every consumer — the schema composition, the validator's checkers, the merkle tree builder, the plan classifier, refresh, the hash-id command and the renderers all read their type-level policy from this one resolution.

## Responsibilities

- **Resolve** the profile per run: `spec/profile.json` beside `project.json` when present — the file sits in `spec/` because it is authored by a person, not written by the tool — or the built-in default otherwise. Absence of the file is the supported default, never an error, which is what [[5392cca550c4|Declare the node taxonomy]] requires: an existing project adopts the mechanism by doing nothing.
- **Validate** the document before anything consumes it. A malformed profile — unparseable JSON, a node type without a plural array key, a field with an unknown kind, a reference field naming an undeclared target type — `module` counts as undeclared here: it is never a declarable type nor a declarable target, and only the frame's own `requires_module` edge names it — an enumeration on a non-text field, bounds on a non-integer field, a duplicate field name within a type, a field name colliding with an envelope field, or a plan-relevant entry naming an undeclared type or a type already listed — is one early, distinct failure naming the file and the defective declaration. The same early path checks the declared [[b1baa51bd7a9|format version]]: a `profile_version` outside the range the binary supports fails with one message naming the file, its version and the supported range — currently exactly version 1, the field-declaration format itself; an absent field means version 1, and a pre-versioning document in the retired `edges`/`hashed_fields` format simply fails validation as malformed, a deliberate breaking change owed no migration signal. Resolution happens once per run before any check, so a broken profile never surfaces downstream as a cascade of schema-conformance errors, which is the early-failure half of [[ef55248cb3ca|Generate schemas from the profile]]. Every spex command resolves the profile before any other work, so a malformed `spec/profile.json` produces the same single early error on stderr and exit 1 — from validate, diff, plan, render and hash-id alike — and no other operation runs.
- **Expose** the resolved profile: the node types (name, plural array key, project-scoped, module-scoped, or both, content-bearing or not, and the two per-type role flags — completeness trigger, name-declarable), each type's field declarations — kind, requiredness, hash participation, enumerations and bounds, and for reference kinds the permitted targets, cardinality and optional `cyclic` exemption — and the graph rules of [[91270a8a2b57|Declare graph rules]]: coverage chains, the plan-relevant list, `plan_relevant` — which node types produce tasks, in the order plan turns into task layers: the declaration the plan gate reads for membership, and whose order [[4c1146bb7287|ChangesetBuilder]] turns into blocking edges between the tasks of adjacent layers; an empty list is legal and declares that no type produces tasks; the list says which types produce tasks and in what order, and nothing about the task lifecycle those tasks then follow, which is plan's and the task-state artifact's business — the per-type impact-level mapping, and refresh's per-type, per-direction absorbable set. Exposure is as interned declarations — each node type and field resolved once, consumers holding and comparing resolved references rather than strings, iteration order being declaration order — which is what keeps per-node work in validate and diff free of repeated name lookups, so the [[afc25fb6c8e8|Fast]] bound and [[b42c5cdf874b|Fast validation]] both hold at 100 modules / 1000 nodes.

## The default profile is the golden policy record

The built-in default is an embedded `defaultProfile.json` — a document in the source tree, parsed at startup, identical in format to what a project may commit as `spec/profile.json`, not hand-authored code values. It declares today's ontology exactly: the five node types with today's role flags and today's field declarations — the reference kinds with the `cyclic` flag omitted on every one, hash participation reproducing the retired allowlists — plus the three coverage links, today's plan-relevant list — data_flow, component, test_section, in that order — impact levels and absorbable directions. It is the single document recording the policy previously spread across seven modules — a newcomer opens it instead of grepping the code — and it is the fixture the golden tests compare against. Each golden comparison uses the equality its artifact warrants: hashes and reports match byte-identically, while the composed schemas match the shipped documents as JSON values, since the shipped copies are hand-formatted and nothing consumes them as bytes. Under the default profile, every identity hash in this repository's own spec is unchanged; the requirement type's title-to-name rename is the one deliberate break, moving each requirement leaf's serialization exactly once — absorbed by the adoption refresh, after which `spex validate` and `spex diff` report as they always have.

## Fixed points

The profile describes a vocabulary; it carries no behaviour and cannot reach:

- the envelope minimum — `id`, `name`, `description`, and `content` where the type is content-bearing — which every declared type carries before its field list begins, the requirement type included: its former `title` field is renamed to `name` by this contract, the one deliberate spec-format break, so the envelope holds universally;
- the identity hash algorithm — already generic over its parts, the type name is just a string segment and the identity is built from field values, which is exactly why the vocabulary can become data, and the rename land, without any identity hash moving;
- the name tokenization rule — relaxing it per project would make removals unsweepable;
- the merkle tree shape — the profile says what leaves exist, never how the tree is built over them;
- the journal event format — append-only and permanent, not per-project.

A profile document attempting to declare any of these fails validation.

## Observability

The resolved profile has no dedicated command. It is observable through `spex render` — the declared types reach the node table — and the reproduce-current-behaviour criterion is enforced by golden tests, not by a surface a user must run.
